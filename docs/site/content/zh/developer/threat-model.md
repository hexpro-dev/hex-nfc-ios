Hex NFC 是一款读取、写入和修改 NFC 标签的工具。本文列出我们防范哪些威胁，以及不防范哪些威胁。

## 范围内

### 数据机密性

- 扫描过的标签存储在设备上的 SwiftData 中，应用没有把这个存储排除在设备备份之外。应用自身的 iCloud 同步需要用户主动开启，默认关闭。开启后，它会把预设和扫描历史镜像到用户的 iCloud 私有数据库中。一条扫描历史条目包含标签的 UID 和记录；对于交通卡，则包含它的 IDm、余额和交易。
- 除 iCloud 同步外，应用只在一种情况下通过网络发送从标签读取的数据。当交通卡显示一个应用无法命名的车站时，用户可以输入名称并点按「提交」，应用会把线路代码、车站代码和地区代码、卡的系统代码以及输入的名称发送到 `api.apps.hex.pro`。这个请求不携带卡上的任何其他内容：既不含它的 IDm，也不含余额或交易列表。
- `PrivacyInfo.xcprivacy` 声明不进行追踪、不收集任何数据类型，上面所说的车站名称建议和反馈留言都没有列在其中。应用还会发出另外四种网络请求，它们都不携带从标签读取的任何内容：Hex NFC 主屏幕会从 `api.apps.hex.pro` 获取开发成本数字，向 `api.p.hex.pro` 请求另一款 Hex Pro 应用的横幅，并下载该响应所指定的图片或视频；反馈表单只在用户点按「发送」时，才会把用户输入的留言、可选的回复地址，以及应用版本、iOS 版本、设备型号和应用语言发送到 `api.hex.pro`。本页没有描述的任何网络请求都属于安全漏洞。
- 应用自身发送给标签的每条命令以及标签的应答，也都会写入 iPhone 的系统日志（子系统 `pro.hex.nfc`，类别 `apdu`），并标记为 `.public`，因此系统不会对其脱敏。发布版本中同样如此，而且没有任何设置可以关闭它。携带密码或密钥的帧会被遮蔽，护照的 BAC EXTERNAL AUTHENTICATE、PACE MSE:Set AT，以及携带认证令牌的最后一条 PACE GENERAL AUTHENTICATE 也会被遮蔽。在此之前的各个 PACE GENERAL AUTHENTICATE 步骤以命令链接方式发送（类别字节为 `10`），遮蔽规则匹配不到它们，因此加密的随机数（nonce）以及为映射和密钥协商而交换的数据会完整写入日志。任何录下无线电交互的人也能得到这些帧。其余一切都会完整写入日志，其中包括：应用检测到的每枚标签的 UID 和交通卡的 IDm；应用读取的配置页；Type 2 标签数据区的前 12 个字节，每次扫描和写入都会读取它们来确认标签仍在；内存转储；应用写入已识别芯片的 Type 2 标签的每条记录；以及读取交通卡余额和交易时所读的块。当 NTAG424 DNA 接受写入所携带的密钥时（仅用该密钥保护写入的标签就会接受），写入发送的记录以及为校验而回读的记录也会完整写入日志。如果标签的 NDEF 文件设置为加密通信（应用正是以这种方式同时保护读取的），这些帧就是加密的。护照的数据组只会以其安全报文（secure messaging）会话中的加密帧形式进入日志。由 iOS 代应用读取的记录不会写入日志，只有在 iOS 以 MIFARE 标签形式呈现的标签上，会写入记录的数量和大小：这包括所有 Type 2 标签、DESFire 卡，以及 iOS 以这种方式呈现的 NTAG424 DNA。任何能读取 iPhone 日志的人，无论是通过连接的 Mac 还是在 sysdiagnose 中，都能读到这些帧。
- 标签保护用的密码或密钥只存储在钥匙串中，作为带有 `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` 的项保存，从不同步，也不会转移到其他设备。它们包括：NTAG21x 和 Ultralight EV1 标签的 4 字节 PWD 和 2 字节 PACK、NTAG424 DNA 的 AES-128 密钥、MIFARE Ultralight C 的 16 字节 3DES 密钥，以及 ICODE SLIX2 的 4 字节写密码。
- 它们存放在两个钥匙串存储中。`KeychainProtectionCredentialStore` 保存开启了保护的预设的密码或密钥，以预设为键；从本机的「库」中删除这个预设时，这份密码或密钥也会随之删除。`KeychainTagCredentialStore` 以标签的 UID 为键。当编辑器「保护」卡片发起的写入应用或移除保护，或者从「库」写入的受保护预设应用保护时，密码或密钥会在新记录写入之后、改变标签保护状态的命令之前保存到这里，排在该标签已有的密码或密钥之前（总共最多 4 份）。保存失败不会中止写入。删除预设不会影响这些条目，应用也没有删除条目的控件：只有在移除保护后的回读显示标签已不受保护，并且已恢复为出厂默认的密码或密钥时，条目才会被删除。目前还没有任何代码会读回条目来解锁标签。在「操作」界面中输入的密码不会保存到任何地方。
- 只有不涉密的*设置*（例如保护从哪一页开始，以及对于 NTAG21x、Ultralight EV1 和 NTAG424 DNA，是仅保护写入还是同时保护读取和写入）会随预设保存、同步或写入 `.hexnfc` 导出文件；密码或密钥从不随之传递。受保护的预设如果通过 iCloud 同步，或通过恢复到新 iPhone 上的备份到达另一台设备，只会带上它的设置，而不会带上密码或密钥。它在「库」中的那一行仍会显示表示会应用保护的锁形图标，但在那台设备上写入它时不会应用任何保护，也不会给出警告。在本机上，开启了保护却没有保存密码或密钥的预设也是如此，例如从一枚扫描到的受保护标签的编辑器中保存、而该编辑器中从未输入过其密码的预设。「另存为预设」面板仍然会说密码或密钥仅存储在本设备上。应用可以把预设共享为 `.hexnfc` 文件，但无法导入这种文件。有两样东西会写入应用临时目录中的文件，而应用两者都不会删除：共享预设时生成的 `.hexnfc` 文件，以及内存转储的 `.bin` 文件，后者在转储完成后立即写入，无论是否共享。
- 只有在用户输入电子护照机读区中的护照号码、出生日期和有效期截止日期之后，应用才会读取护照；这些信息可以手动输入，也可以用相机扫描照片页，相机在设备上读取印刷的文字行，不保留任何图像。应用不会把这些信息，或从护照中读取的任何内容（包括面部图像），保存到扫描历史或应用的任何其他存储中，也不会通过网络发送其中任何内容。结果只在该次会话中显示。

### 破坏性操作的安全

- 在「操作」界面中，有七项操作要求用户先输入标签的完整 UID 才能运行：「擦除」、「格式化」、「移除 NDEF 设置」、「永久锁定」、「尝试次数上限」、「用密码保护」和「移除密码」。「尝试次数上限」仅适用于 NTAG21x 和 Ultralight EV1。「用密码保护」和「移除密码」适用于应用能保护的每一种芯片（NTAG21x、Ultralight EV1、Ultralight C、NTAG424 DNA 和 ICODE SLIX2），标签编辑器的「保护」卡片也能为同样的芯片设置和移除保护。这是输入式确认，而不是选择是或否：输入栏旁显示的 UID 是两次贴合中第一次读取到的 UID，如果第二次贴合的是另一枚标签，操作会被拒绝。
- 「移除 NDEF 设置」会发送 FormatPICC，它会删除 MIFARE DESFire 卡片上的所有应用。它在每次贴合中只用公开的出厂 DES 主密钥认证一次，而且只在同一次贴合已经证明卡片唯一的应用具有本应用的 NDEF 结构、其主密钥为版本 00 的 DES 之后才会这样做。对于带有任何其他应用的卡片（例如交通卡或门禁卡），「格式化」和「移除 NDEF 设置」会在发送任何会改变卡片的命令之前拒绝它。
- 被识别为 NFC 健康设备的标签不会收到任何写入、擦除或控制台命令：它的档案只带有 `.personalHealthDevice`，`refuseIfHealthDevice` 会在发出任何帧之前拒绝 NDEF 写入、内存写入和原始命令。这次扫描从不保存到历史记录。
- 在「操作」界面之外，发布版本中没有任何地方要求这种确认。在编辑器「保护」卡片中应用或移除的保护会作为下一次写入的一部分执行，从「库」写入的预设中的保护也是如此；移除保护仍然需要标签当前的密码或密钥。普通写入会替换标签的内容，删除所有记录后再写入，会像「擦除」一样清空标签。高级控制台会把用户输入的原始命令或从内置列表中载入的原始命令（包括会永久锁定内存或改写配置页的命令）发送出去，每次运行发送给一枚标签，不做任何确认。
- 尝试次数上限（AUTH_LIM）需要用户主动启用，设置它的界面上带有警告。对 NTAG21x 或 Ultralight EV1 应用密码保护时，总会写入上限 0（不限次数），这也会清除标签原有的上限。除了高级控制台中的原始命令之外，非零上限只能在「尝试次数上限」界面中、对已受保护的标签设置。上限为 N 时，标签可以拒绝 N 次错误密码。再错一次，标签就会永远不再接受密码，包括正确的密码，因此它的保护将永远无法移除，受保护的内存也永远无法改写；如果读取也受保护，就永远无法再读取。这是芯片自身的行为，我们会醒目地提示，而不是隐瞒。我们已在 NTAG213 上确认过这个次数。「尝试次数上限」界面也可用于 NTAG213 TT、NTAG215、NTAG216 和 Ultralight EV1，但这些芯片上的次数尚未测试过；NTAG215、NTAG216 和 Ultralight EV1 的数据手册写明了同样的规则。当标签的配置无需密码即可读取时，「尝试次数上限」界面会显示标签已有的上限，这就排除了受读保护的标签。应用永远无法读出标签已经拒绝过多少次错误密码，因为这些芯片上没有任何命令会报告这个数字。
- 永久锁定从来不是预设中的设置，尝试次数上限也不是：从「库」写入的预设可以应用保护，但永远不会永久锁定标签，也不会设置上限。不过，它确实会把同一个密码或密钥写到它所写入的每一枚标签上，而应用从不显示预设所存储的密码或密钥。删除预设的操作是在「库」中它所在的行上轻扫，不需要确认，而且它的密码或密钥不会转移到新 iPhone。开启 iCloud 同步时，在另一台设备上删除这个预设（那台设备上并没有它的密码或密钥），也会将它从本机删除，而它的密码或密钥则留在本机的钥匙串中，不再有任何代码读取。一旦这个预设及其所有副本都被删除，或者用户换用新 iPhone，应用中就不再有任何会发送给标签的副本（上文所述的按标签保存的条目仍留在原来的 iPhone 上，但没有任何代码会读回它们）。除非用户在别处保存了这份密码或密钥，否则用该预设写入的每枚标签上受保护的内存从此都无法再改写。
- 应用从不绕过标签端的认证。如果 Type 2 标签拒绝了我们的 PWD_AUTH，我们会如实报告失败，并且在这次贴合中不再发送第二个密码；我们不会用猜测列表重试。「用密码保护」或「移除密码」被拒绝后，「操作」界面会提供一个按钮**尝试出厂默认值**，它会在一次全新的运行中尝试公开的出厂默认密码，同样需要输入 UID 确认。应用不会自行执行这一步；在设有尝试次数上限的标签上，如果出厂默认密码并不是标签当前持有的密码，这次尝试就算作一次密码错误。对已经仅受写保护的标签运行「用密码保护」时，会把新密码当作标签的当前密码发送，因此在设有尝试次数上限的标签上，除非标签已经持有这个密码，否则这就是一次密码错误。携带密码或密钥的写入会在写入任何内容之前先发送它。这包括存有密码或密钥的预设，以及从编辑器「保护」卡片发起的写入。在应用能保护的每一种芯片上，应用都会先读取标签的保护状态，对读出为未受保护的标签不发送密码或密钥。在「保护」卡片上，发送的值就是刚刚在卡片中输入的值，包括用于替换标签当前密码的新密码，因此在设有尝试次数上限的标签上，只要标签持有的是另一个密码，这就算作一次密码错误。唯一的自动回退发生在 NTAG424 DNA 上：应用或移除保护时，一次会话中最多会用到三个密钥（提供给该操作的当前密钥、公开的全零出厂默认密钥，以及应用保护时的新密钥）。这限制的是尝试的密钥个数，而不是尝试的次数。全新出厂的标签读出为未受保护，因此写入前不会向它发送密钥。更换密钥失败时，还会再尝试最多两次，以确定标签持有的是哪个密钥。我们尚未确定这款芯片是否会对失败的认证计数。

### 构建供应链

- 构建只使用 Apple 框架和 Hex Pro 自己的代码，外加一个仅用于测试的依赖项（`pointfreeco/swift-snapshot-testing`）：没有分析统计或崩溃报告 SDK，也没有第三方 UI 库。这个依赖项声明为从 1.17.0 开始的版本范围，并且没有提交 `Package.resolved`，因此每次全新检出都会解析到该范围内的最新版本。`HexPromoKit` 是从另一个 Hex Pro 仓库的某个固定提交逐字节复制进来的。任何额外的依赖项都是我们不会接受的供应链风险面。
- 发布工作流通过 fastlane Match 以只读方式从一个独立的私有仓库获取签名资源。它使用以 GitHub Actions secrets 形式保存的凭据克隆这个仓库，Match 再用以同样方式保存的口令短语解密这些资源。签名私钥不存放在应用仓库中。发布工具链没有固定版本：工作流每次运行都会从 RubyGems 安装当前的 fastlane 版本，并按主版本标记而不是按提交引用 GitHub Actions。

## 范围外

- 芯片的密码学保证属于芯片本身，芯片是一道硬件信任边界。我们使用芯片提供的任何认证机制；我们并不声称我们的应用能让芯片比其硬件本身更安全。NTAG21x 或 Ultralight EV1 的密码无论是发送还是写入，都会以明文经空中传输。Ultralight C 密钥或 ICODE SLIX2 写密码在写入标签时也是如此。发送 SLIX2 密码时，它只经过一个 16 位随机数的掩码处理，而这个随机数是标签刚刚以明文发出的。任何录下这些交互的人都能得到密码或密钥。
- 我们不防止克隆。NTAG21x 的 UID 在出厂时就已固化，但其余内存可以随意复制到空白标签上。这是整个行业普遍存在的特性，Hex NFC 不会假装能解决它。当 Type 2 芯片返回完整的 32 字节签名时，标签信息卡片会显示“NXP 原厂签名”，但应用从不使用 NXP 的公钥验证它，因此这一行并不能证明标签是真实的。对于任何被识别为具备原厂签名的型号的芯片，「功能」一行都会列出“原厂签名”，无论芯片实际返回了什么。对于 NTAG424 DNA，该卡片会在芯片的功能中列出“SUN 镜像”，但应用既不配置也不检查 SUN 消息。
- 读取护照并不能证明证件是真实的。应用会把读到的数据组与芯片安全对象中的哈希列表进行比较，一致时显示“可能未被篡改”，但它不验证该对象的签名（Passive Authentication），也不运行 Active Authentication 或 Chip Authentication，而这两项才是能发现芯片被复制的检查。
- 任何人只要实际拿到一台已解锁的 iPhone，就能访问上面的标签数据，就像能访问其他任何应用的数据一样。他们还能使用随预设保存的密码和密钥，因为写入预设时，会把其中存储的密码或密钥发送给已用它保护的标签。
- 受攻击者控制的标签可以在响应我们的读取时返回任何数据。我们以防御性的方式进行解析，但除了标签自身的内容以外，我们不会把标签当作任何事情的可信来源。

## 报告漏洞

请通过 [security@hex.pro](mailto:security@hex.pro) 私下报告漏洞，不要在公开论坛中发布。我们会在 72 小时内确认收到报告，然后按照 90 天的协调披露时间表，与报告者一起确定修复方案和公开披露日期。
